A one-line prompt produces a comprehensive project audit. The reason it works is not Claude—it’s what the user built into the project before this session ever started.

I feel like I’ve been playing whack-a-mole for a while, fixing problems and trying to pump out results. Results are still good, obviously. The prompt is vague by design. “Do sort of an audit.” No specific files, no bug reports, no line numbers. The user is tired, knows something is off, and trusts the system to find it. What makes this work is not the prompt—it’s what the prompt is pointing at.

An append-only session log. Every session that modifies the pipeline writes a structured entry at the end: what changed, why, what was left unfinished. The file is referenced in CLAUDE.md as required reading for any orchestrator agent.

This is the infrastructure that makes the vague prompt possible. PROJECT_HISTORY.md isn’t documentation about the project—it’s the project’s memory. This instruction exists in CLAUDE.md, which Claude reads at the start of every session. The audit prompt works because the history it’s pointing at has been dutifully maintained by dozens of previous sessions. The user didn’t have to explain the project’s state—the project explains itself.

Why a vague prompt can work

This session works because the user invested in infrastructure long before it. CLAUDE.md tells every session’s agent to read the project history and write a closeout entry. PROJECT_HISTORY.md accumulates a machine-readable record of what happened, what broke, and what was deferred. When the user finally says “do an audit,” the agent doesn’t need to ask “of what?”—the project’s own documentation tells it where to look.

The audit found issues the user didn’t know about (orphaned entries, prompt contradictions, the JSON corruption vector in apply_triage_batch.py). It found them by comparing what the history says should be true against what actually is. The project’s memory is what made the project auditable.
