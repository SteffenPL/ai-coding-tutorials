The Execution Spec

The document that a fresh agent reads to run the entire pipeline. This is what persistent, session-independent infrastructure looks like.

You are the orchestrator for a multi-stage scRNA-seq database curation pipeline. You sequence the stages, run scripts between them, dispatch subagents, and present results to the user.

Stage 1 (Search) → you run scripts →
Stage 2 (Triage) → you run scripts →
Stage 3 (Paper read) → you run scripts →
Stage 4 (Feedback audit) → report to user → apply corrections

You are the ONLY agent that runs scripts or modifies the database. Subagents are pure readers that return structured output.

The first thing any orchestrator agent sees. Two rules: here's the pipeline, and here's who's allowed to touch the database. One agent writes; everyone else reads.

Stage 3 is strict simultaneity. It confirms that at least one piece of data at the accession is simultaneously human scRNA-seq, published, and public. It does not summarize papers, observe, or enumerate data units. The unit-enumeration work that older stage 5 prompts did is archived in archive/agent_prompts/ for possible future resurrection as a downstream stage.

The simultaneity rule—first noticed in the design session as "we want all of these things at once"—is now a single sentence in the orchestrator spec. The archived stage 5 reference is a trace of the pipeline's own history: features that were tried, retired, and preserved rather than deleted.

If the user interrupts at any point, save progress by applying whatever decisions have been made so far.

If a major part of the pipeline is not working out, consult with the user rather than silently skipping or redoing batches. Entire batches have been lost historically because orchestrators chose to press on through a broken stage instead of pausing.

The last sentence is a scar. That happened. The instruction exists because the next agent shouldn't make the same mistake.

Agents write to disk. Stage 3 agents write to data/stage3_output/<accession>.json. Do not rely on parsing agent conversation output—always use the disk files.

Subagent write permissions: Agents that need to write files (stage 3, paper recovery) may be blocked by permission prompts they cannot accept. Before dispatching any batch of file-writing agents:

1. mkdir -p the output directory.

2. Write a trivial seed file (e.g. data/stage3_output/.warmup) using the Write tool. This triggers the user's permission approval, which then carries through to subagents in the same session.

Two rules born from operational pain. The first: agent output goes to files, not conversation text, because conversation text disappears when context overflows. The second: the "permission warming" trick—invented by the user in a later session when subagents couldn't write their results—is now baked into the spec.

· · ·

What NOT to delegate to subagents:

• Running scripts (db_update.py, build_database.py, fetch_papers.py, apply_stage3.py, apply_triage_batch.py, etc.)

• Selecting the audit sample (you choose which entries stage 4 sees)

• Applying corrections to the database

• Deciding whether to proceed after errors

The orchestrator picks what gets audited. Not the subagents, not chance. And when something breaks, the orchestrator asks the user—it doesn't push through. Both of these rules were written after sessions where the opposite happened.

What this document is

This is 400 lines of instructions that any fresh Claude Code session can read cold and immediately run a multi-stage curation pipeline on thousands of database entries. No prior conversation needed. No summary of what happened last time. The document is the context.

Every rule in the "lessons learned" section is a scar from a real session. Permission warming, disk-first output, don't press on through errors—all of these were discovered the hard way and then written down so the next agent wouldn't have to rediscover them.
