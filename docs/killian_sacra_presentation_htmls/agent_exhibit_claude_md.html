# CLAUDE.md This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository. ## Project Overview A curated database of scRNA-seq datasets from NCBI BioProject. Accessions are organized into per-accession directories (`database/PRJNAxxxxxx/`) with structured metadata. The master JSON lives at `data/bioproject_search_data.json`.

The agent’s cheat sheet. Every script it needs, with exact invocations. The mundane parts are most of it—and that’s the point. A CLAUDE.md that covers the boring stuff means the agent never has to guess how to run a test or update a field.

## Architecture ### Gate-Based Schema Four binary exclusion gates determine entry status: - `is_human`, `has_scrnaseq`, `has_publication`, `has_public_data` - Values: `yes` / `no` / `unclear` / `unchecked` - **Derived status** (never stored, always computed): - PASS = all gates `yes` - FAIL = any gate `no` - INCOMPLETE = no `no` but some `unclear`/`unchecked` - Everything else (cell_type_relevance, tumor, platform, etc.) is a **descriptive tag**, not an exclusion gate. - Structural fields (not gates, not tags): `review_depth`, `in_reference_list`, `parent_bioproject` ### Data Flow `data/search_queries_bioproject.json` → `bioproject_search.py` (NCBI API) → `data/bioproject_search_data.json` → `build_database.py` → `database/PRJNAxxxxxx/INDEX.md` The master JSON (`bioproject_search_data.json`) is the single source of truth. INDEX.md files are generated from it. All mutations go through `db_update.py` which updates both the JSON and the INDEX.md. ### Key Directories - `src/scrna_database/` — Python package (NCBI API wrapper, CSV generation) - `scripts/` — All operational scripts (the primary interface for database operations) - `database/` — Per-accession directories using PRJNA IDs (INDEX.md, METADATA.md, paper.md, figures/) - `data/` — Master JSON and search queries - `archive/` — Old tissue-specific runs (germ_cell, kidney) - `reference/` — Collaborator reference data ### Script Philosophy Always use pre-built scripts in `scripts/` for database operations. Do not write ad-hoc Python to manipulate `bioproject_search_data.json` directly. The scripts handle JSON/INDEX.md synchronization and validation. ### NCBI API Rate-limited to 0.35s between requests (NCBI compliance). UIDs are cached in `bioproject_search_data.json` to avoid re-querying. Batch fetching uses 100 UIDs per esummary request.
## Subagent Pipeline Database curation uses a 4-stage subagent pipeline, orchestrated by a managing agent. Agent instruction prompts: `docs/agent_prompts/`. The retired stage-5/6 unit-extraction prompts live at `archive/agent_prompts/` for possible future resurrection as a downstream stage. ### Stages | Stage | Role | Model | Batch size | |---|---|---|---| | 1. Search | Construct BioProject queries, collect UIDs | Sonnet | 1 per tissue | | 2. Triage | Metadata gate-setting, reject obvious non-matches | Sonnet | 20–30 entries | | 3. Paper Read | Confirm simultaneous human scRNA-seq + published + public; emit 2 paper-level tags | Sonnet | ~10 entries | | 4. Feedback | Audit samples from stages 2 and 3 until no mistakes remain | Opus | 3–5 entries | ### Reference lists are for validation, not input When a collaborator provides a reference list of datasets, it is a **benchmark**, not an import list. Do not add entries to the database because they appear on a reference list. Instead, run the normal pipeline and check afterward how many reference entries surfaced naturally. Discrepancies are diagnostic: - **Reference entry not found by pipeline** → query coverage gap. Investigate whether search terms, database scope, or filters need adjustment. - **Reference entry found but classified differently** → check carefully. The reference list can be mistaken. Explain the discrepancy fully; if the pipeline’s classification is correct, document why. - **Reference entry found and matches** → validation success. The `in_reference_list` flag marks entries that appear on a collaborator’s list, for tracking purposes only. It has no effect on pipeline behavior. ### Key principles - **Orchestrator runs all scripts** — subagents are pure readers/classifiers that produce structured output. They never call `db_update.py` or modify files. - **Stage 3 is rigid** — it confirms that at least one piece of data at the accession is *simultaneously* human scRNA-seq, published, and publicly available. No summarization, no narrative, no unit enumeration. Four gates + two tags (`data_origin`, `cell_type_relevance`) and that is all. - **Stage 3 does not trust triage** — it re-confirms every gate from the paper. - **Traceability** — each stage has clear blame boundaries. Wrong gate on a classified entry = stage 3’s fault. False negative rejection = stage 2’s fault. - **Stage 4 is self-obsolescing** — it audits stage-2 rejections, stage-2 accepts, stage-3 PASS, and stage-3 FAIL samples. Its value is proportional to how many mistakes it surfaces; it runs until it stops finding them.
### Careful documentation of all modifications. When a script is updated, when agent prompt files are updated, when some step of the orchestrator pipeline is completed on a batch of data, when realizations of systematic errors are found by the phase 3 or 4 agents; the main agent MUST update PROJECT_HISTORY.md. (Subagents, from the orchestration pipeline for example, are NOT to make updates to PROJECT_HISTORY.md.) Updates should be prefaced by a date and agent self-identifier (related to what you consider your role to be in this directory), such that repeat modifications by the same agent will be identifiable. Updates should be added linearly. Do not edit previous entries. If a previous entry shows some mistake in understanding or implementation that we have fixed, simply note as much down in your own entry. Do not wax overly verbose, but summarize changes (or even pontifications on todos and the like) how you see fit.

The last section of the file. The agent is told to keep a journal—dated, signed with a self-chosen name, appended linearly, never revised. If an earlier agent was wrong, the current agent notes the correction below it. The permission to include “pontifications on todos and the like” is deliberate: the log is for thinking out loud, not just recording facts.

What a CLAUDE.md is

A file in the root of a project directory. Every time Claude Code opens a session there, it reads this first. The mundane parts—the commands, the file paths, the test runner—mean the agent never has to guess how to do routine work. The interesting parts are the prohibitions: don’t write ad-hoc code, don’t trust the previous stage, don’t import the reference list. Each one exists because, at some point, the opposite happened.
