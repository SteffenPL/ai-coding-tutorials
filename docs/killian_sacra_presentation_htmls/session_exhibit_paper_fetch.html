Can you tell during the search if papers are being skipped or abandoned by error messages? If so, we could try to resolve those while we’re waiting.

537 entries labeled “paywalled.” The user starts thinking about what that actually means.

Lets think about the paywalled papers for a second. In this case, is the pubmed version or some other archive version usually available? There are basically three things to think about here. 1: does a paper exist. 2: can we provide the paper link to the users of the browser, even if we cannot access it. 3: can we download ANY version of the paper, archive included, in order to help the subagents parse it with a deep read.

A fuzzy problem—“paywalled papers”—decomposed into three precise levels. Each has different requirements and different solutions. Does it exist? Can users see it? Can agents read it?

Yes. Lets do a few things here. First, multiple fallbacks to get something, ending at the abstract if nothing else. Second, we’ll need a new field, even if hidden, for passing entries telling us WHAT version of the paper was obtained.

The user doesn’t just want a workaround—they want the system to know what kind of paper it has. An abstract is better than nothing, but the pipeline should know it’s working with an abstract.

· · ·

Those 2,677 entries without PMID/DOI should never have been labeled “paywalled” — they were victims of the catch-all bug. The script’s error handling treated every failure as a paywall, including entries that simply had no publication identifier at all.

The second discovery. The first session found that triage was rejecting entries with real publications. This session finds that the fetch script was labeling entries “paywalled” when they had no identifiers at all. Same blind spot, different symptom.

fetch_papers.py enhanced with a 5-level fallback chain: PMC HTML → DOI publisher → Europe PMC → Unpaywall API → PubMed abstract. New paper_source field tracks which level succeeded.

The solution addresses all three levels from the user’s decomposition. Full text where possible, abstract as a last resort, and a metadata field recording what the pipeline is actually working with.

Re-fetch complete: 1,542 of 1,556 previously-paywalled entries recovered. 99.1% success rate.

Paper coverage jumped from 4,221 to 5,763 — a 37% increase in a single session.

One user prompt, three precise questions, five fallback levels. Fifteen hundred papers that the pipeline thought were inaccessible.

We haven’t done an audit in a while, is that right?

Right — the last audits were back on April 18–19. Since then we’ve pushed through 422 entries at Stage 3 with no audit.

A simple question that triggers one more discovery. The audit finds Stage 3 confusing “paywalled/abstract-only” with “unpublished”—setting has_publication: no despite a PMID existing. The same false-negative pattern from fd80b335, now appearing at a different pipeline stage.

The same problem, three times

Session fd80b335 finds the blind spot at triage: entries rejected as “no publication” because a metadata field is empty. Session 4da6b918 implements the script-level fix and discovers its limits—mechanical lookup catches 25%, but judgment calls need agents. Session 3174b856 finds the problem again at fetch: entries labeled “paywalled” because an error handler treats every failure the same way. Three sessions, three angles on a single truth: publications are invisible to the machine not because they don’t exist, but because the metadata linking them is unreliable.

The fix isn’t a single change. It’s a prompt correction at Stage 2, a spec document handed off between sessions, a title-lookup script layered with a paper-recovery agent, a 5-level fallback chain in the fetch script, and a new schema field to track provenance. Each session contributed a piece. Each piece required the ones before it.

The user’s three-part decomposition in session 3174b856—does it exist, can users see it, can agents read it—is the moment the problem stopped being about “paywalled papers” and became an engineering question with a layered solution.
